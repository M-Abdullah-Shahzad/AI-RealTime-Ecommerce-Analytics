# Viva Preparation — E-commerce Analytics and Streaming Demo

## 1. What problem does the project address?

It demonstrates how transaction data can be cleaned, analyzed, segmented into customer groups, used for exploratory inactivity classification, and examined for product associations. It also includes a separate Kafka/Spark streaming demonstration.

## 2. What dataset is used?

The project expects the Online Retail II transaction CSV. The dataset is downloaded separately and placed at `data/online_retail_II.csv`. It is not stored in this repository.

## 3. What does the cleaning module do?

It normalizes selected column names, removes rows without customer IDs, filters cancelled invoices, removes non-positive quantities and prices, drops duplicate rows, converts dates and customer IDs, and creates `TotalPrice = Quantity × Price`.

## 4. What is RFM analysis?

- **Recency:** time since the customer's most recent purchase.
- **Frequency:** number of transaction rows/purchases represented by the aggregation.
- **Monetary:** total customer spend.

RFM is used for descriptive customer segmentation, not as a causal explanation of customer behavior.

## 5. What does the churn classifier currently predict?

The target is defined as no purchase in the final 90 days of the observed dataset. This is a retrospective inactivity label. It should not be presented as a validated prediction of whether a customer will churn in a future period.

## 6. Why was Recency removed from the Random Forest input features?

Because the target is directly defined from the same end-of-period recency value. Feeding that value to the model would leak the target definition into the input. The model currently uses other customer aggregates. Even with Recency excluded, the task remains retrospective and requires temporal validation before being described as future churn prediction.

## 7. Why use Random Forest?

Random Forest combines multiple decision trees and can model nonlinear relationships in customer-level features. It is a reasonable exploratory baseline, but its usefulness depends on a sound target definition, representative data, and independent evaluation.

## 8. What is Kafka doing?

The producer replays rows from the cleaned transaction CSV to a Kafka topic named `retail_orders`. It simulates a stream of transaction events; it is not connected to a live retail checkout system.

## 9. What is Spark Structured Streaming doing?

The Spark consumer reads Kafka messages, parses their JSON payload, converts timestamps, and calculates windowed sales aggregates. The current demo prints the results; it does not persist them to the Streamlit dashboard.

## 10. Is the dashboard real-time?

No. The Streamlit dashboard reads CSV outputs generated by the batch modules. Kafka/Spark is a separate demonstration and is not currently connected to the dashboard.

## 11. What is Apriori?

Apriori finds frequent itemsets and derives association rules. Support measures how often an itemset occurs, confidence estimates the conditional frequency of the consequent given the antecedent, and lift compares the observed co-occurrence with what independence would imply.

## 12. Are the business insights generated by an LLM?

No. The insight module uses deterministic rules and descriptive statistics. The project does not call a generative AI model for this component.

## 13. What are the main limitations?

- The inactivity target is retrospective, not forward-looking.
- A time-based feature/label split and temporal holdout are needed for future churn prediction.
- The dashboard uses batch CSV files.
- Kafka events are replayed historical rows.
- Streaming aggregates are not persisted to the dashboard.
- The dataset and generated artifacts must be downloaded or generated locally.
- No measured ROI or production-readiness claim is supported by the current repository.

## 14. What would be the next engineering steps?

1. Create a proper temporal churn target using a historical feature window and a later outcome window.
2. Evaluate with a chronological holdout and report precision, recall, F1, ROC-AUC, and calibration.
3. Persist Spark aggregates to a database or streaming sink.
4. Connect the dashboard to the persisted stream aggregates.
5. Add data validation, automated tests, and repeatable deployment checks.
